# 1. Docs as Code

The dossier is a Git repository of Markdown documents, machine-readable specifications (OpenAPI, AsyncAPI), the poker reference implementation with its test vectors, and ADRs.

- **Source of truth:** the Markdown files and specs in Git (`main`).
- **PDFs** are generated by `tools/build.py` into `dist/pdf/` for people outside the team (counsel, regulators, test labs, investors, operators). PDFs are never edited by hand.
- When the code monorepo is created, this repository becomes its `docs/` folder (KP-ENG-11 §1).
- The Bridge Casino dossier remains a separate repository until Bridge is integrated (gate G4); decisions in this dossier supersede Bridge decisions where they conflict (KP-ENG-01 §12).

# 3. Versioning

- **Major (2.0):** change of scope or a decision that invalidates earlier content.
- **Minor (1.1):** added or changed sections, with a "What changed" note.
- **Patch:** typos and clarifications; Git history is enough.
- Legal drafts stay at 0.x until counsel approves them (1.0).

# 4. Change Process

1. Branch and edit the Markdown (or spec).
2. Pull request with the template; link tickets or a change request for scope, schedule or budget.
3. Reviews: document owner (CODEOWNERS); cross-cutting changes also need owners of affected documents; certified-scope documents (KP-ENG-06, KP-ENG-13, KP-LEG-07) need the compliance officer.
4. CI: spec generation and validation, `check_api_consistency.py`, `check_references.py`, reference vectors, PDF build.
5. Merge; the PDF set is rebuilt and attached to the dossier release when needed.

# 5. Status and Approval

@widths 1.4,3.6
| Status | Meaning |
|---|---|
| Draft | Work in progress |
| In review | Content complete; awaiting owner and stakeholder approval |
| Approved | Baseline; changes need an approved pull request |
| Living document | Updated continuously (risk register, ADR log, glossary) |
| DRAFT for counsel review | Legal documents that must not be used externally before counsel approval |

# 6. Consistency Rules

- Cross-cutting decisions live in KP-ENG-01 §3 and the ADRs; they win over other documents, which are corrected in the same pull request.
- Terminology follows the glossary (KP-GOV-02).
- API facts live in the generated specs; prose documents are checked against them automatically.
- Every document ID referenced anywhere must exist (`tools/check_references.py`).
- Game-rule examples are generated by the reference implementation, not typed by hand.

# 7. Dossier Reviews

Monthly status review by the Programme Director; full review of documents relevant to each gate (G1–G4) with sign-off in KP-OPS-06.
